# Интеграция KStom Case Designer с DentalDB: предложение ведущему

Исполнитель: Codex · Ветка: follower/dentaldb-integration-plan · База: `0af4d67` · 10.11.2026.
Состояние: исследование и предложение; интеграция не реализована, каркас и границы файлов задаёт ведущий.

## Цель и основной сценарий

Заказ сохраняется в DentalDB → кнопка «KStom Case Designer» открывает именно этот заказ → КТ, сканы,
совмещение, монтаж, реабилитация → «Подготовить для DentalCAD» собирает согласованный комплект в папке
заказа → штатная кнопка Design открывает результат. Выбор папок и ручное копирование сеток на каждом кейсе
убираются. Индикации, материалы, номера зубов и сведения заказа остаются под управлением DentalDB.
Для варианта уже начатой работы сначала используется штатный Duplicate в DentalDB.

## Что подтверждено, а что ещё проверить

- exocad документирует `StartButtonList` / `ExecPath` / `Params`: `%p` — путь текущего `.dentalProject`.
  В установленной DentalDB 3.3 такие вызовы действительно есть, включая стороннее ПО и DentalCAD.
- `.dentalProject` — официальный контекст обмена; внешняя программа может записывать файлы сканов рядом.
- Сейчас `app/main.py` не принимает проект; `exocad_articulator_export.export` создаёт отдельную копию,
  запрещает непустой выходной каталог; регистрация копии в DentalDB остаётся ручной (`docs/exocad.md`).
  Это готовый сборщик значительной части данных, но ещё не полноценный коннектор DentalDB.
- Новый заказ из KStom — отдельный маршрут: официальный минимальный `.dentalProject`, затем его штатный
  импорт и разворачивание материалов. DPMCI документирован exocad, но в проверенной установке не найден.
  Его наличие и способ импорта нужно подтвердить; генерацию полного заказа нельзя объявлять готовой
  по одному факту появления XML-файла. Идентификаторы копии/заказа при импорте также требуют проверки.
- Автоимпорт у отдельных сканеров существует; универсальный автоматический импорт нашего заказа
  для этой установки не подтверждён. Командный запуск CAD сам по себе не регистрирует заказ в DentalDB.
- `.partialInfo` уже используется для привязки костей и корней к челюстям. Автоподгрузка и движение
  в чистом заказе с реальными индикациями требуют проверки; менять тип реставрации ради костей нельзя.

## Предлагаемый контракт для каркаса

1. Вход: `KStomCaseDesigner.exe --dental-project <абсолютный путь>`; существующий режим запуска сохраняется.
   Точный выбор файла вместо «первого найденного в папке»; пробелы, кириллица, UNC, несколько проектов.
   В работающий экземпляр передаётся контекст явно; одновременная работа с двумя заказами не смешивает кейсы.
2. Контекст: идентификатор связи, выбранный проект, его ревизия, роли сканов и матрицы; продолжение работы
   по локальному `.ccdcase`. Новый контекст не заменяет несохранённую работу молча. В памяти/диагностике
   и интерфейсе демонстрации — только номер кейса, без имён и открытых путей; данные пациента не дублируются
   в отдельной базе KStom. Приватные файлы связи — только вне Git в каталоге кейса/данных пользователя.
3. Сборка: один снимок состояния, одна система координат и выбранный прикус для всех ролей. Сканы челюстей,
   исходные сканы прикуса с ясным назначением, кости, корни, карта десны, маркер, `.jawmotion`, параметры
   артикулятора, эстетические виды/фото и паспорт. Реабилитация и движения должны соответствовать друг другу.
   Сборщик выдаёт манифест ролей, матриц, ревизии и контрольных сумм; сканы не подменяются по имени наугад.
4. Публикация: пакет сначала полностью готовится и проверяется во временной папке на том же томе.
   Для публикации нескольких файлов нужны журнал и откат: набор не становится атомарным от одного `os.replace`.
   При ошибке, отмене, заполненном диске или недоступной сети исходный заказ остаётся пригодным для открытия.
   Перед заменой проверяются ревизии/хеши и принадлежность файлов: чужие моделировки/каркасы не перезаписываются.
   Переделка геометрии в заказе с существующей `.dentalCAD` требует отдельного варианта заказа.
5. Завершение: публикация подтверждается только после проверок файлов, затем DentalCAD запускается с точным
   проектом штатным вызовом. Пути передаются списком аргументов, без shell. Возврат и обновление DentalDB
   после завершения внешней программы проверяются на ПК; одного успешного завершения KStom недостаточно.
6. Обратная связь: изменения официальных `.scanInfo`, `.matrix4`, `.constructionInfo` и выходных сеток
   обнаруживаются по событию с повторной проверкой стабильности файлов. Автоматически читать/предлагать
   обновление можно; заменять исходный прикус/монтаж по изменённой сцене без явной операции нельзя.
   Изменённая одновременно другой программой ревизия — конфликт с понятным выбором, без цикла перезаписей.

## Порядок реализации и приёмка

- Ведущий: контракт контекста заказа, вход CLI, сборка в текущий заказ/новый вариант, модель ревизий и
  владения файлами, контрактные тесты. Существующий экспорт копии сохраняется отдельным сценарием.
- Ведомый после передачи: подключение запуска из DentalDB, импорт сканов по ролям, возобновление кейса,
  сборка/проверка/публикация, обработка конфликтов и окно результата. Настройка кнопки — отдельная операция
  с резервной копией и откатом; в рамках этого исследования файлы DentalDB/exocad не изменялись.
- Первая приёмка на Windows: новый заказ DentalDB → KStom → готовые файлы → Design, без ручного поиска
  и копирования файлов; повторное открытие того же кейса; отмена; повторная публикация; два разных заказа.
- Проверки файлов: все ссылки существуют, матрицы применены ровно один раз, версии/хеши согласованы;
  кости движутся со своей челюстью, движения стартуют из выбранной реабилитационной позы; чужие файлы сохранены.
- Вторая приёмка: импорт нового заказа, созданного вне DentalDB, корректная регистрация без дубликатов
  и проверка материалов. До этого этапа основной поддержанный сценарий — запуск из сохранённого заказа DentalDB.
